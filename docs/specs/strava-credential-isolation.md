# Strava credential isolation

> Human designer: Crash (BigGillyStyle)

## 1. Summary

The Slackbot uses a member's Strava connection without exposing OAuth credentials
through editable profile metadata. Connections belong to F3 users across Slack
workspaces and are never carried into sanitized database copies.

## 2. Context & links

- Apps affected: API, Me and Slackbot.
- Store: [database schema](../../packages/db/drizzle/schema.ts) and
  [Python models](../../packages/db-python/f3_data_models/models.py).
- Integration: [credential access](../../apps/slackbot/infrastructure/strava_credentials.py).
- Copies: [staging refresh](../STAGING_REFRESH.md).

## 3. User stories

- A connected member can use Strava without disclosing tokens to profile readers.
- An authorized profile editor can maintain profile data without replacing the
  member's connection.
- An operator can sanitize a database copy without carrying usable connections
  into another environment.

## 4. Acceptance criteria (testable, non-contradictory)

- **AC-1** — Profile list, detail, self and mutation responses remove every
  top-level `strava_*` metadata key, irrespective of PII permissions. Other
  object metadata retains its existing contract; non-object values remaining
  after database decoding return null rather than exposing serialized content.
- **AC-2** — Profile writes explicitly supplying any such key fail with
  `BAD_REQUEST`, without a partial profile update. Ordinary profile edits do
  not change the credential store.
- **AC-3** — OAuth exchange and refresh persist complete bundles only in
  `user_strava_credentials`. Missing rows or a not-yet-created table mean
  disconnected; no operation falls back to metadata or creates schema at runtime.
  Other database failures remain errors.
- **AC-4** — The store enforces one row per F3 user and unique athlete ownership.
  Slack identity lookup includes both member and workspace before resolving
  the F3 user. Refresh and reconnect updates serialize so an older refresh
  cannot overwrite a completed reconnect. A connection attempt for an athlete
  owned by another F3 profile returns HTTP 409 with a support message and leaves
  both profiles' existing credentials unchanged; it never transfers ownership.
- **AC-5** — Backfill imports only missing user connections. Existing rows win
  unchanged, including when legacy values differ. Cross-user athlete ownership
  conflicts and invalid data abort the transaction with value-free diagnostics.
- **AC-6** — Legacy `strava_*` metadata keys and obsolete Slack credential
  columns are cleared. Both sides of user audit snapshots are scrubbed in the
  same transaction, including snapshots generated by the cleanup. Audit identity,
  attribution, timing and unrelated data are retained; the shared trigger is
  unchanged. Null or absent metadata is preserved; non-object metadata fails
  closed. Repeating the history transformation changes nothing.
- **AC-7** — Sanitized copies remove legacy metadata keys, empty the dedicated
  store and discard legacy Slack credentials in both ordinary and
  preserve-local-seed modes.

## 5. Roles & authorization (RBAC)

| Action                          | Allowed                                                  | Explicitly denied                                            |
| ------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------ |
| Use or update connection        | Server-side Strava integration for the linked F3 user    | General profile routes and API keys                          |
| Read or edit other profile data | Existing procedure tiers and resource-scoped permissions | Any extra privilege inferred from owning a Strava connection |
| Copy database                   | Authorized operators using sanitization                  | Unsanitized connection transfer                              |

The table is an application boundary; deployed database-role isolation requires
separate verification of grants.

## 6. Out of scope / non-goals

- Broader metadata allowlisting and unrelated OAuth authorization changes.
- Automatic credential revocation, member notifications, backup rewriting or
  advisory publication.

## 7. Deployment and rollback constraints

Operational closure requires deployed verification and an assessment of whether
staging and production share Strava authority or application secrets, including
any exposure that requires separately authorized remediation.

The release owner must deploy the API protections, bot and sanitized copy tooling
before migrating. Normal Cloud Run draining applies. A temporary disconnected
state is acceptable; migration must follow promptly. Manual staging refresh must
wait for sanitized tooling. Restoring an old metadata-writing bot is not a safe
rollback. These are active rollout constraints, not permission to execute a
shared-environment migration.

Pending migrations run atomically: failure of the data migration also rolls back
creation of the credential table when both are pending. Non-object live or audit
metadata, incomplete legacy bundles without a stored connection, conflicting
athlete ownership, invalid identifiers/expiry, and lock timeouts abort the batch.
The release owner must check these data conditions read-only before rollout and
resolve failures before retrying; members remain disconnected while the store is
absent. Profile writes that replace metadata before backfill can remove legacy
connections, requiring those members to reconnect.

Cleanup verification covers live metadata and both sides of audit snapshots
after in-flight profile writes finish. A whole-object metadata write that read
before cleanup can restore legacy keys after the transaction commits.

## 8. Critical-path test cases

- Real API profile reads and rejected writes, including privileged and self paths.
- Complete exchange/refresh, missing store, provider failure and serialized updates
  using synthetic credentials.
- Actual SQL backfill with a fresh reconnect, legacy-only connection, audit
  snapshots, repeat execution and complete rollback on failure.
- Sanitization with credentials in each storage location and both copy modes.

## 9. Observability

Record operation outcomes without tokens, provider responses, authorization
headers or SQL parameters. Local verification uses synthetic values only.
